# Seeded Workout — Design Spec

**Date:** 2026-07-31
**Status:** Approved

---

## Context

The app stores workouts in IndexedDB via Dexie (`src/db/db.ts`). Every workout in
the list is user-created through `/new`; a fresh install shows an empty state.

We want one built-in workout — a 10-minute, 10-exercise HIIT routine — to be
delivered to every install so the app is useful before the user has created
anything.

---

## Requirements

1. The workout is inserted **once per database**, for existing installs as well
   as fresh ones. An install that already holds user-created workouts still
   receives it on the next load.
2. After insertion it is an **ordinary workout**. It can be run and deleted like
   any other. Deleting it is permanent — it does not come back on reload.
3. Insertion must not be observable as a flash of empty state followed by a card
   popping in.
4. A failed seed must not break the app.

Explicitly out of scope: an "undeletable built-in" concept, per-exercise
coaching descriptions, and an edit screen. See *Rejected alternatives*.

---

## Seed content

| Field | Value |
|---|---|
| Seed id | `ten-minute-hiit-v1` |
| Workout name | `10-Minute HIIT` (14 chars; `LIMITS.workoutNameChars` is 40) |
| `prepareDelay` | `true` |
| `prepareSeconds` | `10` (`DEFAULT_PREPARE_SECONDS`) |

Ten rounds, identical apart from the exercise name:

| Field | Value |
|---|---|
| `mode` | `'time'` |
| `value` | `40` |
| `restTime` | `20` |
| `secondsPerRep` | `3` (`DEFAULT_ROUND.secondsPerRep`; ignored in time mode but required by `Round`) |

Exercises, in order:

1. Jumping Jacks
2. High Knees
3. Switching Lunges
4. Butt Kicks
5. Squat Taps
6. Burpees
7. In & Outs
8. Switching Mountain Climbers
9. Plank Side to Side
10. Bicycles

Longest exercise name is `Switching Mountain Climbers` at 27 chars, within the
30-char `LIMITS.exerciseNameChars`.

Round 10 keeps `restTime: 20`, which the schema treats as the cool down. Work
plus rest is therefore 10×40s + 10×20s = **600s (10:00)**, matching the name.

Note that `estimateWorkoutSeconds` (`src/lib/duration.ts:10`) counts the prepare
delay as well, so the workout card displays **10:10**. This is accepted: the
lead-in is real time, and every user-created workout is measured the same way.
Tests assert 600s for work+rest and 610s for the estimate, so both numbers are
pinned deliberately rather than by accident.

## Architecture

### `src/db/seeds.ts` — seed data

Plain data, no I/O. The ten rounds are generated by mapping the exercise-name
list, so `order` is correct by construction.

```ts
import type { NewWorkout } from './workoutRepo'   // type-only: no runtime import

export interface WorkoutSeed {
  /** Stable and never reused. Recorded in `appliedSeeds` once delivered. */
  id: string
  workout: NewWorkout
}

export const WORKOUT_SEEDS: WorkoutSeed[] = [ /* ten-minute-hiit-v1 */ ]
```

`WORKOUT_SEEDS` is an array rather than a single constant so a second built-in
workout later is one entry plus one new id, with no change to the delivery
mechanism.

### `src/db/schema.ts` — new type

```ts
export interface AppliedSeed {
  /** WorkoutSeed.id */
  id: string
  appliedAt: number
}
```

### `src/db/db.ts` — schema v2 and wiring

```ts
db.version(1).stores({ workouts: '++id, lastUsedAt, createdAt' })
db.version(2).stores({
  workouts: '++id, lastUsedAt, createdAt',
  appliedSeeds: 'id',
})
```

Version 1 stays declared so existing databases upgrade cleanly. The change is
purely additive; no existing workout is touched.

`HiitDb` is exported as a type so `seed.ts` can accept the database as a
parameter without a runtime import.

Wiring goes at the bottom of the module:

```ts
db.on('ready', () =>
  applySeeds(db, WORKOUT_SEEDS, Date.now()).catch(err =>
    console.error('Workout seeding failed', err),
  ),
)
```

### `src/db/seed.ts` — delivery

```ts
import type { HiitDb } from './db'          // type-only: erased, no import cycle
import type { WorkoutSeed } from './seeds'

/**
 * Inserts every seed whose id is not yet recorded in `appliedSeeds`.
 * Returns the ids applied. A seed is delivered exactly once per database —
 * deleting the resulting workout does not bring it back.
 */
export async function applySeeds(
  db: HiitDb,
  seeds: WorkoutSeed[],
  now: number,
): Promise<string[]>
```

The body runs a single `rw` transaction across `workouts` and `appliedSeeds`:
read the applied ids, filter `seeds` to the pending ones, then for each pending
seed `add` the workout (`createdAt: now`, `lastUsedAt: null`) and `add` the
marker.

## Design decisions

**`db.on('ready')`, not `on('populate')`.** `populate` fires only when the
database is first created, so existing installs would never receive the seed —
that fails requirement 1. `ready` fires after the database opens but before any
queued operation runs, and returning a promise holds every query until seeding
resolves. This satisfies requirement 3 directly: `useLiveQuery` on the list
screen cannot observe a pre-seed state.

**Marker in IndexedDB, not localStorage.** The marker must survive deletion of
the seeded workout (requirement 2), so it cannot be derived from the workouts
table. Keeping it in the same store as the data means clearing site data resets
both together. A localStorage marker can desync permanently — deleting the
IndexedDB database from DevTools without touching localStorage would lose the
seed with no way to recover it.

**`db` is a parameter of `applySeeds`.** `db.ts` imports `seed.ts` and never the
reverse. Tests call `applySeeds` against any database instance, and `now` is
injected the way `createWorkout` already does it.

**`applySeeds` does not reuse `createWorkout`.** That function renumbers `order`
from array position because it normalizes untrusted form input; seeds are
authored data whose `order` is already correct. Reusing it would also force
`seed.ts` to import the live `db`, defeating the parameter injection above. A
direct `add` keeps the module free of runtime imports.

**Insert and marker share one transaction.** A crash mid-way rolls back both, so
the next load retries cleanly rather than leaving a marker with no workout.

**The `ready` handler swallows its own errors.** A rejected `ready` handler
fails `db.open()`, leaving the app with an unopenable database and a list that
never loads. Catching means a broken seed costs the seeded workout, not the app
(requirement 4).

**Seed sorts to the top of the list.** `createdAt` is stamped at seed time, and
`sortByRecency` falls back to `createdAt` for never-used workouts. On an install
with existing workouts the new seed appears first, which matches how a
just-saved workout behaves.

## Rejected alternatives

| Alternative | Why not |
|---|---|
| Undeletable built-in (`builtIn` flag, delete disabled) | Requires a schema flag and list-screen UI changes. The user wants it deletable once delivered. |
| Re-seed whenever missing | Deleting would feel broken — the workout returns on every reload. |
| Hardcoded, never stored | The list and runner would both need to handle a workout that has no database row. |
| Seed only when the list is empty | Never reaches an install that already holds workouts, and re-seeds after the user clears the list. |
| Explicit `await seedWorkouts()` in `main.tsx` | Blocks first paint on every load, and the "database is seeded" invariant stops being owned by the database module. |
| Per-exercise `description` field | Needs a schema migration, a create-form input, and runner/pre-start UI. Its own project. |

## Testing

### `src/db/seeds.test.ts` — pure data assertions, no IndexedDB

Guards against a bad edit to the seed content, the likeliest future breakage.

- 10 rounds, `order` contiguous 1…10
- workout name within `LIMITS.workoutNameChars`; every exercise name within
  `LIMITS.exerciseNameChars`
- every `value` and `restTime` inside `LIMITS` — a seed the create form would
  reject is a bug
- work plus rest sums to 600s, and `estimateWorkoutSeconds` returns 610s — the
  card's displayed total, pinned so a change to the prepare delay is a visible
  test failure rather than a silent shift
- seed ids are unique across `WORKOUT_SEEDS`

### `src/db/seed.test.ts` — behaviour, `fake-indexeddb/auto`

- applies a pending seed on an empty database; the workout is retrievable with
  the right name and round count
- a second call returns `[]` and adds nothing — idempotent
- deleting the seeded workout, then re-running, does not bring it back
- a seed whose id is already in `appliedSeeds` is skipped even when no matching
  workout exists
- a failure mid-transaction leaves no marker behind, so the next run retries

### Existing suite

`workoutRepo.test.ts` imports `db`, so the `ready` hook now fires there too.
Dexie queues its `beforeEach` clear behind the seed promise, so those tests are
expected to pass unchanged — this is an assumption to verify by running the
suite, not to assert.

### Not tested

The `db.on('ready')` registration itself. Exercising it means opening a real
database and asserting on module-load side effects, which is brittle for one
line of wiring that the manual check covers directly.

### Manual verification

1. Load the app; confirm the `10-Minute HIIT` card appears reading 10:10
   (600s of work and rest plus the 10s prepare delay).
2. Open it and start; confirm exercise names show in the timer ring.
3. Delete the card, reload; confirm it stays gone.
4. Create a workout, reload; confirm the seed is still absent and the new
   workout is intact.
